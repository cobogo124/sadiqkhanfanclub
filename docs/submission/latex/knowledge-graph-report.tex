\section{Knowledge Graph Report}\label{knowledge-graph-report}

\subsection{Introduction}\label{introduction}

This project develops a knowledge graph for London public
transportation, centred on the Transport for London (TfL) network and
covering lines, stations, zones, operators, accessibility, fares, and
night services. The chosen domain matches the coursework brief closely
and supports a varied set of competency questions spanning operational,
accessibility, and fare-related knowledge.

The repository implements an automated multi-stage construction pipeline
rather than relying on manual graph authoring. The current build is
orchestrated by \texttt{main.py}, which generates the ontology schema
through \texttt{generateOntology.py}, enriches it with GTFS-aligned
modelling, ingests structured TfL API data, processes unstructured
Wikipedia text, and merges the outputs into
\texttt{ontologies/pipeline\_output/final\_london\_transport\_kg.ttl}.
The current final graph contains 26,156 triples and is approximately 1.1
MB on disk.

This automated design aligns well with the brief\textquotesingle s
emphasis on combining structured and textual sources, ontology reuse,
mapping pipelines, and AI-assisted extraction. The current revision is
especially strong in three areas:

\begin{itemize}
\tightlist
\item
  consistent use of the canonical \texttt{http://example.org/tfl\#}
  namespace across most generated entities
\item
  programmatic ontology generation and cache-backed reproducibility
\item
  richer provenance and broader source coverage than the earlier
  snapshot
\end{itemize}

The public repository linked to this submission is:

\begin{itemize}
\tightlist
\item
  \href{https://github.com/cobogo124/sadiqkhanfanclub}{sadiqkhanfanclub}
\end{itemize}

\subsection{Data Source Selection}\label{data-source-selection}

\subsubsection{Structured sources}\label{structured-sources}

The main structured source is the TfL Unified API, cached locally as
\texttt{downloads/tfl\_api\_cache.json}. This is the most appropriate
structured source in the repository because it provides authoritative
operational data directly from the transport authority, including:

\begin{itemize}
\tightlist
\item
  line names and identifiers
\item
  stop-point metadata
\item
  zone information
\item
  service-status information
\item
  selected facility and accessibility attributes
\end{itemize}

The committed cache is around 79 MB and includes 695 line records
together with 7,949 nested stop-point entries. In the current pipeline,
\texttt{data\_retrieval/structured\_retrieval/tfl\_api\_processor.py}
reads this cache directly when present, which makes the committed data
both the main structured source and the most reproducible input for
marking.

As a supplementary structured resource, the repository also contains
\texttt{downloads/naptan\_london.csv}, which is useful for stop and
station normalization. In addition, the historical files
\texttt{docs/generated/tfl-sources.json} and
\texttt{docs/generated/tfl-sources.md} remain useful as evidence of
earlier source discovery and selection work, even though the present
pipeline revision no longer regenerates them directly.

\subsubsection{Textual sources}\label{textual-sources}

The unstructured stage draws primarily on Wikipedia pages selected in
\texttt{data\_retrieval/unstructured\_retrieval/wiki\_scraper.py}. The
current source list contains 66 article entries, of which 59 are unique.
The coverage is intentionally broad so that the graph can capture facts
that are difficult to obtain reliably from operational APIs alone, such
as:

\begin{itemize}
\tightlist
\item
  line and station descriptions
\item
  operator and service background
\item
  night-service information
\item
  payment-system and fare context
\item
  accessibility-related descriptions
\item
  infrastructure and interchange details
\end{itemize}

The article inventory includes pages for major Underground lines,
interchange stations such as King\textquotesingle s Cross St Pancras and
Stratford, night-service topics, Oyster and Travelcard concepts, bus
operators, and infrastructure pages. This is a good fit for the
coursework because it complements the structured TfL data with narrative
facts that support competency questions on history, operation,
accessibility, and payment.

\subsubsection{Source-selection
rationale}\label{source-selection-rationale}

The overall source strategy follows a sound knowledge-engineering
pattern:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The TfL API provides authoritative operational facts and identifiers.
\item
  Wikipedia provides broader contextual facts that are useful for
  ontology population and competency-question coverage.
\item
  Local caches preserve reproducibility and reduce dependence on live
  external services during repeated runs.
\end{enumerate}

This combination is well aligned with the brief because it demonstrates
genuine multi-source construction rather than a graph built from a
single dataset.

\subsubsection{Reproducibility notes}\label{reproducibility-notes}

The current repository is designed to run reproducibly from committed
caches, while still supporting a configurable live extraction path when
needed. The main practical points are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The structured pipeline uses the committed TfL cache by default.
\item
  The unstructured pipeline preserves a large extraction cache in
  \texttt{data/caches/triples\_cache.json}.
\item
  The live LLM extraction path can be configured locally when a fresh
  extraction run is required.
\item
  The source inventory remains explicit in code, making it easy to
  inspect and refine.
\end{enumerate}

\subsection{Extension Of Existing
Ontologies}\label{extension-of-existing-ontologies}

The knowledge graph reuses and extends two established ontologies:

\begin{itemize}
\tightlist
\item
  GTFS (\texttt{http://vocab.gtfs.org/terms\#})
\item
  Schema.org (\texttt{http://schema.org/})
\end{itemize}

This is a strong modelling choice because both vocabularies are already
well suited to transport, journeys, agencies, stations, and pricing
concepts. The current ontology is built programmatically by
\texttt{generateOntology.py}, which gives the project a reproducible
TBox and a clear record of all classes and properties added by the team.

\subsubsection{Examples of subclass
extensions}\label{examples-of-subclass-extensions}

The current ontology includes multiple subclasses that extend imported
concepts, for example:

\begin{itemize}
\tightlist
\item
  \texttt{tfl:TfLLine\ rdfs:subClassOf\ gtfs:Route}
\item
  \texttt{tfl:TfLStation\ rdfs:subClassOf\ gtfs:Station}
\item
  \texttt{tfl:OysterFare\ rdfs:subClassOf\ schema:PriceSpecification}
\item
  \texttt{tfl:TfLOperator\ rdfs:subClassOf\ gtfs:Agency}
\end{itemize}

The ontology then refines these further with domain-specific subclasses
such as:

\begin{itemize}
\tightlist
\item
  \texttt{tfl:UndergroundLine\ rdfs:subClassOf\ tfl:TfLLine}
\item
  \texttt{tfl:NightTubeLine\ rdfs:subClassOf\ tfl:UndergroundLine}
\item
  \texttt{tfl:NightBusRoute\ rdfs:subClassOf\ tfl:BusRoute}
\item
  \texttt{tfl:UndergroundStation\ rdfs:subClassOf\ tfl:TfLStation}
\item
  \texttt{tfl:PeakFare\ rdfs:subClassOf\ tfl:OysterFare}
\end{itemize}

These extensions are closely tied to the coursework domain and make the
graph much more expressive than imported ontologies alone.

\subsubsection{Examples of subproperty
extensions}\label{examples-of-subproperty-extensions}

The ontology also defines subproperties that align the local model with
established vocabularies, for example:

\begin{itemize}
\tightlist
\item
  \texttt{tfl:servedByLine\ rdfs:subPropertyOf\ gtfs:route}
\item
  \texttt{tfl:operatesInZone\ rdfs:subPropertyOf\ gtfs:zone}
\item
  \texttt{tfl:operatedBy\ rdfs:subPropertyOf\ schema:provider}
\item
  \texttt{tfl:fareAmount\ rdfs:subPropertyOf\ schema:price}
\item
  \texttt{tfl:routeNumber\ rdfs:subPropertyOf\ gtfs:shortName}
\end{itemize}

These choices are important because they preserve compatibility with
external ontologies while still allowing the project to express
transport-specific semantics such as station facilities, accessibility
features, disruptions, journey legs, and fare zones.

\subsubsection{Benefits of the current ontology
approach}\label{benefits-of-the-current-ontology-approach}

The programmatic generator provides several advantages:

\begin{itemize}
\tightlist
\item
  the ontology can be rebuilt deterministically
\item
  domain additions are visible in a single implementation file
\item
  imported ontologies are declared explicitly
\item
  the class and property hierarchy remains easy to inspect and extend
\end{itemize}

Overall, the ontology work satisfies the brief well by combining reuse
with meaningful domain-specific extension.

\subsection{Mappings}\label{mappings}

\subsubsection{Structured mapping
pipeline}\label{structured-mapping-pipeline}

The structured mapping stage is implemented primarily in
\texttt{data\_retrieval/structured\_retrieval/tfl\_api\_processor.py}.
It reads the TfL cache, normalizes identifiers into the \texttt{tfl:}
namespace, and emits graph facts from API fields and stop metadata. The
current structured stage contributes:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  line entities and labels
\item
  station and stop related facts
\item
  zone assertions
\item
  accessibility flags
\item
  facility assertions such as toilets and car parks
\item
  service-status and disruption-related information where available
\item
  night-bus classification based on route naming conventions
\end{enumerate}

This stage is a strong part of the current architecture because it
grounds the graph in authoritative operational data and produces a large
share of the graph\textquotesingle s directly verifiable transport
facts.

\subsubsection{Unstructured mapping
pipeline}\label{unstructured-mapping-pipeline}

The unstructured stage combines web-scraped text, chunking, prompt-based
triple extraction, and RDF materialization. The main workflow is:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  select domain-relevant Wikipedia pages in \texttt{wiki\_scraper.py}
\item
  split long text into chunks with \texttt{CHUNK\_SIZE\ =\ 1000}
\item
  extract candidate triples with the constrained prompt in
  \texttt{extract\_triples.py}
\item
  reuse cached extractions where available
\item
  filter low-value outputs with \texttt{remove\_junk(...)}
\item
  convert validated triples into RDF in \texttt{triples\_to\_rdf.py}
\item
  add enrichment links such as inverse connections and normalized zones
\end{enumerate}

This is a good example of AI-assisted knowledge engineering because the
prompt is not used in isolation. Instead, it is embedded inside a
broader pipeline with filtering, normalization, and ontology-aware RDF
construction.

The current extraction cache contains 1,442 entries, which shows that
the project has already accumulated substantial prompt-driven extraction
work. The repository snapshot is configured for cache-backed
reproducibility, while the live extraction path can be enabled locally
when needed.

\subsubsection{Merge and build stage}\label{merge-and-build-stage}

The final build is assembled in \texttt{main.py}. The process starts
from the generated ontology schema, then merges outputs from structured
and unstructured stages into a single final graph. This is an important
strength of the current design because it demonstrates an end-to-end
construction system rather than isolated scripts.

The merged artifact also includes substantial provenance coverage, with
1,268 subjects linked to explicit \texttt{dcterms:source} values and 50
distinct Wikipedia source URIs represented in the final graph. This
strengthens the transparency of the knowledge graph and supports
downstream evaluation.

\subsection{Queries}\label{queries}

The repository includes 20 competency questions together with an
executable validation harness in
\texttt{competency\_questions/competency\_question\_test.py}. This is
valuable because it ties the graph directly to the project requirements
and provides a concrete way to measure whether the knowledge graph
answers the intended questions.

On the current final graph, the stored SPARQL harness returns non-empty
results for 12 out of the 20 competency questions. This gives a current
non-empty answerability score of:

\begin{itemize}
\tightlist
\item
  12/20 answered
\item
  60\% non-empty query coverage
\end{itemize}

The present query set is strongest on operational and service-oriented
questions. Representative examples include:

\begin{itemize}
\tightlist
\item
  CQ1: King\textquotesingle s Cross St Pancras returns a clear set of
  intersecting Underground lines
\item
  CQ4: DLR returns zone information
\item
  CQ5: the Jubilee line query returns step-free-access-related station
  results
\item
  CQ17: night bus routes return a substantial set of \texttt{N}-prefixed
  services
\end{itemize}

This means the graph is already supporting a meaningful part of the
intended question set through executable SPARQL queries. The remaining
questions provide a focused target list for the separate
completion-analysis work required by the brief.

\subsection{Evaluation Methodology}\label{evaluation-methodology}

\subsubsection{Quality metrics}\label{quality-metrics}

The evaluation strategy focuses on metrics that are appropriate for an
automated coursework knowledge graph:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  competency-question answerability through executable SPARQL queries
\item
  qualitative review of returned answers for relevance and precision
\item
  graph coverage metrics such as number of triples and populated domain
  areas
\item
  provenance coverage
\item
  ontology-conformance checks during inspection of generated entities
  and predicates
\end{enumerate}

Useful current graph indicators include:

\begin{itemize}
\tightlist
\item
  final merged graph size: 26,156 triples
\item
  subjects with explicit \texttt{dcterms:source}: 1,268
\item
  distinct Wikipedia source URIs represented in the graph: 50
\item
  night bus routes: 75
\item
  public toilets: 43
\item
  car parks: 27
\item
  assisted boarding features: 2
\item
  fare concessions: 5
\end{itemize}

These figures show broad automated coverage across several important
parts of the domain, especially services, facilities, and provenance.

\subsubsection{Performance metrics}\label{performance-metrics}

A fresh local measurement on the current final graph gives:

\begin{itemize}
\tightlist
\item
  parse time: about 1.26 seconds
\item
  total 20-query evaluation time: about 0.29 seconds
\item
  average per-query time: about 0.015 seconds
\item
  peak resident memory during that run: about 61 MB
\end{itemize}

These results indicate that the graph is lightweight enough to load and
query efficiently in a coursework setting, while still being large
enough to demonstrate a substantial automated build.

\subsubsection{Evaluation
considerations}\label{evaluation-considerations}

The current repository supports reliable evaluation because:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  the final graph is committed and directly testable
\item
  the SPARQL competency-question harness is executable
\item
  key data sources are cached locally
\item
  prompts and mapping code are preserved in the repository
\end{enumerate}

As with any evolving automated pipeline, some evaluation dimensions
benefit from iterative refinement, particularly for the subset of
questions that depend on narrowly targeted benchmark instances. Those
areas are documented in the completion analysis and in the separate
engineering note.

\subsection{Conclusion}\label{conclusion}

The current repository demonstrates a credible automated knowledge-graph
construction system for the London public-transport domain. It combines
structured TfL data, unstructured textual extraction, ontology reuse,
domain-specific extensions, provenance capture, and executable SPARQL
evaluation in a single reproducible workflow.

The strongest aspects of the project are its clear multi-source design,
programmatic ontology generation, cache-backed reproducibility, and
measurable support for a substantial portion of the competency-question
set. Taken together, these features align well with the brief and
provide a solid basis for the completion and prompt-analysis documents
that accompany the report.
